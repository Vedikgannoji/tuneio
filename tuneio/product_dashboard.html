Understand your API before you optimize it.

tuneio sits between your client and an existing API. Route requests through the proxy to measure real traffic, then approve public read rules when caching makes sense.

01

Run your API

Your upstream stays a separate process. For the RAM-only review fixture:

python examples/cache_upstream.py
Terminal 1 · upstream on port 3000
02

Start the proxy

Point a validated config at your API. Observation is the default.

tuneio serve --config autotuner.json
Terminal 2 · keep this terminal running
03

Send traffic through it

Use the Playground or your own client. Requests sent directly to the upstream do not enter proxy telemetry.

curl.exe http://127.0.0.1:8080/your/endpoint
Terminal 3 · the playground also works here

Your first config

From the folder where you want the config:

tuneio init --upstream http://127.0.0.1:3000
tuneio config check --config autotuner.json
tuneio serve --config autotuner.json

Then open a separate terminal:

tuneio dashboard --config autotuner.json

This development checkout installs with python -m pip install -e ".[test]". Public package publication is a later release step.

Read the numbers correctly

Proxy latency
Handling through response completion. It includes admission and downstream waits.
Upstream I/O
Actual upstream work; excludes local admission and downstream send waits.
Console round trip
Your browser's request to this console. It includes control and preview overhead.
Throughput
Completed retained requests divided by the whole selected time window.

These measurements are useful observations, not a controlled speedup benchmark.

Why am I seeing no data or no cache hits?

No traffic

Keep both upstream and proxy terminals running, then send requests to the proxy address. Opening this dashboard does not generate API traffic.

No eligible reads

Writes, credentials, range/conditional requests and unsupported response semantics bypass shared caching. Policy cards show the reason.

Observing or fast origin

Adaptive policies need enough valid samples and recent same-key reuse. A fast API can correctly stay uncached.

Expired or invalidated

Expiry and declared mutations require a fresh origin response. The next request may MISS before later HITs.

Cache off

Observe, recommend and off modes do not serve responses from the cache. Recommend records hypothetical decisions only.

Storage fault

Live forwarding can continue while persistence is degraded. Inspect storage drops and incomplete-history flags; unavailable data is not zero latency.

Approve caching deliberately

Only declare public GET resources. Cache-Control, Age, Date, Vary and configured byte limits still gate every entry. Add mutation dependencies for all related reads, including reports. External writes bypassing this proxy cannot participate in its invalidation generations.

Use mode: "cache" with policy: "cache" for fixed TTL, or mode: "adaptive" with approved adaptive policies for automatic activation and bounded TTL tuning. Edit configuration and restart to change modes. This local profile is single-worker and requires no management token.

The scenario runner previews writes and stops dependencies after an unexpected result. Captures are restricted scalar fields; no arbitrary code is evaluated. A cancelled or timed-out write may have committed upstream: inspect state, and do not assume it was rolled back.
